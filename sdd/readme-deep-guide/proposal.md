# 提案：README 開發歷程深度導讀

> 用 `deep-guide` skill 把 `README.md`（839 行、Append-only 對話紀錄）轉化成一篇說故事的導讀文，涵蓋這個專案從開案到自動化資安檢查的完整歷程。

## 為什麼做

`README.md` 目前是原始的逐輪對話紀錄格式（USER/AI 交替、Append-only），適合追溯細節，但不利閱讀全貌——839 行裡混雜著實作細節、色碼、指令輸出，沒有讀過全程的人很難一次抓到「這個專案經歷了什麼」。使用者希望有一篇用敘事方式整理、能看出完整脈絡的導讀文。

## 要改什麼

1. 已通讀 `README.md` 全文（839 行，分兩段讀取），整理出完整時間線與五個階段：
   - **開案**：提案 PDF 轉 JPG 純前端工具，技術可行性評估（PDF.js + JSZip），SDD 提案確認
   - **開發**：依 tasks.md 逐條實作，含 TDD 測試 Runner、資安風險初評
   - **驗收與歸檔**：7 項任務打勾、歸檔至 `sdd/archive/`
   - **兩輪 UI/UX + 資安複審**：模擬資深工程師視角挑出共 19 項問題（第一輪 12 項 + 第二輪 7 項）逐一修正，含 CSP、SRI、鍵盤可用性、WCAG 對比度、RWD、配色從深色系 → 淺色系 → 再生紙質感三次迭代
   - **上架部署**：初始化 git、合併遠端既有 GitHub Pages workflow、推送
   - **自動化資安檢查**：背景 commit 安全審查抓到 3 項 CSP/供應鏈問題並修正、後續主動執行 Claude Security 全專案掃描（0 發現，verified），並把掃描結果做成 `test.html`/`index.html` 互相連動的公開紀錄
2. 用 `deep-guide` skill 的五段式敘事結構（痛點先行 → 靈魂拷問 → 機制解構 → 深層真相 → 落地價值）把上述歷程寫成一篇連貫的導讀文，語言為繁體中文台灣用語，**文字要生動活潑**，不出現寫作技法名稱或角色扮演。
3. 導讀文除了時間線，必須融入使用者指定的四個敘事主軸（這些是這個專案真正發生過的事，不是虛構）：
   - **主軸一：指令下達與「對齊」**——貫穿全程的提案→確認→實作循環，就是使用者反覆用文字把自己腦中的畫面同步進 AI 認知的過程；每一輪「請確認」都是一次對齊檢查點，對齊了才准動手。
   - **主軸二：計畫先落地成檔案，不流於對話**——`proposal.md`／`tasks.md`／`plan.html`／`plan-review2.html` 這些實際存在的規劃檔案，就是「先寫清楚、不是說說而已」的具體證據，符合 SDD＋TDD 規範（規格先行、測試先行、確認才動手）。
   - **主軸三：實作後的美感落差要靠共同畫面聚焦**——配色從深色系 → 淺色米白 → 再生紙質感，三次迭代都是使用者用主觀感受的字眼（「protect eyes」「不要太亮」「再生紙的感覺」）描述，AI 每次都算出對比度、截圖給使用者核對，用「同一張截圖」當作雙方都看得到的共同基準，才把主觀感受收斂成具體色碼。
   - **主軸四：資安檢查踩著新工具的節奏走**——先是背景自動審查抓到問題並修正，接著使用者主動抓住 Claude 剛推出的 Claude Security 掃描 plugin，對整個專案跑了一次全面掃描（0 發現、三人小組驗證），把「資安不只做一次」的態度也寫進故事裡。
4. 建立資料夾 `path/`（沿用使用者指定的資料夾名稱）存放這篇導讀文，檔名 `path/pdf-to-jpg-開發旅程導讀.md`。

## 影響範圍

- 新增檔案：`path/pdf-to-jpg-開發旅程導讀.md`（純文件，不影響任何產品程式碼）
- 不修改 `index.html`／`css`／`js`／`test.html`／`plan.html` 等既有檔案
- 不影響 git 版控狀態以外的任何功能；產出後可自行決定是否 commit

### 補充：對「path 資料夾」命名的理解
使用者原文為「建立path資料夾」，本提案直接照字面理解為資料夾名稱就是 `path`。若原意是其他名稱（例如取自「旅程 path」的比喻但想用別的命名），請在確認時告知，一併調整。
